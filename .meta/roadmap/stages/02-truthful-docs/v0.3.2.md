## Objective
Make the public API self-documenting and buildable as HTML. Every
user-facing property/method has a docstring with visible types; a Sphinx
project under `docs/` builds clean HTML against the in-tree docstrings. No
hosted site yet — that lands in `v1.0.0` — just the local skeleton.

## Goals
- Docstring audit across the public API surface:
  - `pptx/api.py`
  - `pptx/presentation.py`
  - `pptx/slide.py`
  - `pptx/shapes/` (`base.py`, `autoshape.py`, `picture.py`, `connector.py`,
    `group.py`, `freeform.py`, `placeholder.py`, `graphfrm.py`, `shapetree.py`)
  - `pptx/text/text.py`
  - `pptx/chart/chart.py` and the rest of `pptx/chart/`
  - `pptx/dml/` (`color.py`, `fill.py`, `line.py`, `effect.py`)
  - `pptx/table.py`, `pptx/action.py`
- For each public property and method: docstring exists, names parameters
  and return type in prose, references the relevant OOXML element/attribute
  in backticks (`a:ln`, `c:dLbls`, etc.) where it clarifies intent.
- Sphinx scaffold under `docs/`:
  - `docs/conf.py` — minimal config; `sphinx.ext.autodoc`,
    `sphinx.ext.napoleon`, `sphinx.ext.intersphinx` enabled; `pypptx` package
    on `sys.path`.
  - `docs/index.rst` — top-level TOC.
  - `docs/api/*.rst` — autodoc stubs for the modules listed above.
  - `docs/_build/` added to `.gitignore`.
- Add `docs` extra to `pyproject.toml` (`sphinx`, `sphinx-autodoc-typehints`).
- Add a one-line developer-workflow note to `CLAUDE.md` under "Common
  Commands": how to invoke `sphinx-build`.

## Implementation notes (added when the work started, 2026-09-30)
- **Module list as built.** The card's list plus the public modules it missed:
  `shapes/altcontent.py`, `shapes/range.py`, `text/styles.py`, `dml/chtfmt.py`,
  `dml/threed.py`, and `chart/chartex.py`; plus a units/utilities page for `pptx.util` and
  `pptx.exc` (every length is a `Length`, most errors a `pptx.exc` class). The chart writers
  (`xmlwriter.py`, `chartexwriter.py`, `xlsx.py`) are left out: their public-named classes
  (`ChartExXmlWriter`, `CategoryWorkbookWriter`, …) are machinery `add_chart` drives, not
  objects a caller holds. `pptx.enum.*` gets its own page (`docs/api/enum.rst`).
- **API defined on private classes.** Much of the API lives on underscore bases
  (`_BaseGroupShapes.add_shape`, `_BaseSeries.name`, `_BaseAxis.*`), so autodoc shows
  inherited members on the public subclasses (standard-library bases excluded). Private
  classes a caller is handed directly — `_Paragraph`, `_Run`, `_Hyperlink`, `_Cell`, `_Row`,
  `_Column` and their collections, `_Plots`, `_Background`, `_PlaceholderFormat`,
  `_MediaFormat`, `_OleFormat`, `_GradientStops`/`_GradientStop` — get explicit `autoclass`
  entries.
- **Substitutions.** Docstrings use the python-pptx `|Name|` convention. `docs/conf.py` builds
  `rst_epilog` from every class defined in a `pptx` module, plus `|True|`/`|False|`/`|None|`,
  a few builtins, and conceptual names whose base class is private (`|Series|`, `|Plot|`,
  `|Axis|`). Each name is defined once; classes in documented modules win a name clash, and the
  module-qualified form (`|data.Category|`) reaches either. An unknown `|Name|` stays undefined
  and fails `-W`. A known name whose class is not rendered links nowhere without a warning;
  `sphinx-build -n` would list those, and is not part of this version's bar.
- **Enum labels.** `:ref:\`MsoLineDashStyle\``-style references resolve to labels on the enum
  page, one per enum, named by CamelCasing the class name (and the "MS API Name" when it differs).
- **Napoleon vs. colons.** Napoleon reads a property's first line as `type: description` and
  splits it at any colon — `` `a:ln` ``, a `:ref:` role, or prose. A docstring hook leads every
  property/attribute docstring with an empty RST comment so napoleon finds no inline type;
  `default_role = "literal"` renders every `` `a:ln` `` as code.
- **Intersphinx** maps Python only (the lxml inventory returned 503). The build needs network
  for it; offline, `-W` fails on the unreachable inventory.

## Dependencies
- `v0.3.1` merged so docstrings can reference the canonical example scripts

## Out of scope
- Publishing to Read the Docs or GitHub Pages — `v1.0.0` work.
- Hand-authored narrative documentation beyond what `automodule` /
  `autoclass` emit (no tutorials, no "user guide" prose).
- API changes prompted by the audit — file them as TODO entries against
  `v0.4.0` instead.
- Internal-module docstrings (`pptx/opc/`, `pptx/oxml/`, `pptx/parts/`) — out
  of scope until the public surface is solid.

## Objectives / acceptance
- `sphinx-build -W -b html docs docs/_build/html` succeeds with zero warnings
  (the `-W` flag promotes warnings to errors).
- Spot-check the built HTML: every module in the audit list has an
  autodoc-rendered page, and every public class on those pages has at least
  a one-line summary.
- `pytest -q` remains green (a docstring audit can accidentally invalidate
  doctest-style assertions if any exist).
- `mypy` / `pyright` (if run locally) report no new "missing docstring"
  diagnostics on the audited modules — `py.typed` annotations remain consistent with the new
  docstrings. [Neither tool emits such a diagnostic, so this was checked as "no new
  pyright/ruff findings" plus a script finding 0 undocumented public members.]
